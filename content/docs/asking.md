好的问题不要求你已经知道答案。它只是让别人不必猜测你的处境，也让你在整理时更接近原因。

## 发出问题前，整理五件事

1. **目标**：你原本想完成什么？别只描述自己选中的某一种解决办法。
2. **环境**：操作系统、相关软件与版本。只提供和问题有关的信息。
3. **步骤**：从一个可说明的起点，到出错之前，依次做了什么？
4. **现象**：预期结果、实际结果和完整的关键报错。文字报错尽量直接复制，代码放进代码块。
5. **尝试**：已经检查过哪些地方？每次尝试分别得到什么结果？

## 可以直接使用的提问结构

下面各项是填写提示，不是已经发生的问题。发送前用你自己的真实信息替换；没有的信息就说明暂时不知道。

```text
目标：我想完成的事情。
环境：系统、相关工具及版本。
操作步骤：从哪里开始，依次做了哪些操作。
预期结果：我认为应该发生什么。
实际结果：发生了什么，附关键报错原文。
已经尝试：尝试的方法，以及每一种方法的结果。
需要帮助：我现在最不确定的是哪一步。
```

如果是网页问题，可以补充浏览器、页面路径以及是否稳定复现；如果是代码问题，尽量给出能独立复现的最小片段。不要为了“最小”把关键输入或报错上下文一起删掉。

## 去哪里问

- **编程与学习问题**：到[学码编程交流群](/join/)交流。
- **本站错字、链接或内容问题**：在 [本站 GitHub 仓库](https://github.com/HustCAteam/cateam) 提 Issue 或 PR，附上页面路径。
- **Touranki 的体验问题**：先按上面的结构记录，再通过[项目入口](/projects/)或交流群确认反馈渠道。

在群里直接说明问题即可，不必只发“有人吗”。不要重复刷屏、私信轰炸，也不要把自愿帮助当成即时客服。

## 信息安全比截图完整更重要

{{< callout type="warning" >}}
发送日志和截图前，检查访问令牌、密码、账号、学号、邮箱、文件路径中的个人身份信息，以及屏幕边缘的私人聊天。用不影响复现的替代值说明结构，绝不发送真实密钥。不要将包含这些信息的内容复制到公开 Issue。
{{< /callout >}}

硬件问题先说明设备状况与数据是否已备份。涉及拆机、电源或重要数据时，暂停不确定的操作，确认风险和责任边界；线上建议不能保证设备与数据安全。

## 解决后，留下一句总结

说明最终原因、有效的方法，以及哪些尝试无效。如果问题仍未解决，也可以补充新线索。之后将通用经验整理到[共学手册](/docs/)，一次求助就能成为下一次协作的起点。
